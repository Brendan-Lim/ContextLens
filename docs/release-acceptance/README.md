# Exact-candidate interactive acceptance

There is deliberately **no `0.3.1.json` acceptance record**. Its absence blocks official publication. `template.json` contains pending cases and intentionally fails the gate.

1. Manually dispatch **Official Unnotarized Candidate and Promotion**, operation `prepare`, from main with the version in `config/version.json`. This performs CI, one ad-hoc app build, both packages and round-trip checks. It uploads a 30-day Actions artifact; it does not create a tag or release.
2. Download that exact candidate artifact. Verify `SHA256SUMS`; retain its ZIP, DMG and `provenance.json` unchanged. On a disposable interactive Mac, use a genuine quarantined download to observe first-launch policy. An Actions download/locally copied app that never receives quarantine cannot prove Gatekeeper first-launch behavior.
3. Follow every required [beta acceptance step](../beta-acceptance.md), including Low and High capture, selected-window closure with another window present, target-app exit, ContextLens exit during capture, failed save/retry and persisted pending frames. Also inspect the actual Finder installer in light and dark modes and perform the real drag/copy/eject/launch flow. Preserve raw synthetic evidence privately.
4. Copy the template to `VERSION.json`. Copy `version`, `build`, `sourceCommit`, `bundleInventorySHA256` and `assets` **verbatim from the tested provenance**. Record a real tester identifier (a public handle is sufficient), an ISO 8601 `testedAt` timestamp with timezone offset, macOS version, architecture and `isolatedEnvironment: true`. For example, an actual observation at noon UTC would use `2026-11-09T12:00:00+00:00`; supply the real past observation time, not this example. Timezone offsets ensure a tester's date is compared as the same instant on a UTC runner. Every case must have `status: "pass"`, a substantive observation and a safe evidence locator. Describe the actual Gatekeeper warning/decision; if Open Anyway is unnecessary under the recorded policy, state why. Do not mark an unobserved case passed. `blockers` must be empty only after findings are resolved.
5. Review the evidence with a maintainer, audit its contents for publication, commit and push the record. It is an accountable human attestation; JSON validation cannot prove that a GUI observation occurred. Never put personal desktop images, account identities, machine serial numbers or raw logs in this directory.
6. Dispatch operation `promote` with that successful prepare run ID, the version, and the exact confirmation `PUBLISH UNNOTARIZED VERSION`. The script requires current clean main, an unused version, the original successful official workflow/source, source ancestry and exact acceptance/asset/bundle matches. It re-verifies both containers, creates a draft, redownloads and verifies uploaded bytes, then publishes `ContextLens vVERSION` without a preview suffix. No rebuilding occurs during promotion.

If a candidate changes, repeat acceptance for its new hashes. If its artifact expires, prepare a new candidate and repeat acceptance. A failed publication may leave a tag/draft: inspect it and resolve deliberately; the script refuses automated replacement or clobbering. The Developer ID workflow remains independent and requires its original signing/notarization credentials.

## Candidate freshness

The earlier prepare run `42504640955` predates the Hand Off reliability changes and is obsolete for v0.3.1. Do not promote its ZIP/DMG or reuse its hashes or acceptance. Use the replacement candidate recorded in [the final candidate report](../final-0.3.1-candidate.md).

New official bundles embed a versioned `releaseInputs` SHA-256 inventory in `official.json`, repeated in `provenance.json`. It binds every tracked input path, Git object ID and executable/symlink mode. The build dependency closure includes Swift source and the embedded CLI, SwiftPM manifests/lockfiles, all scripts and imported helpers, version/signing configuration, icon/license/resources, DMG artwork/layout/packaging and pinned dependencies, and workflows/toolchain configuration. Unknown/new files are protected by default, including files under docs. No production dependency is added.

The only exceptions are regular non-executable files explicitly listed in `config/release-input-policy.json`, plus this version's exact acceptance JSON path. The policy's documentation entries were reviewed against the actual build/package readers; a new documentation path needs an explicit policy change, which itself invalidates existing candidates. Symlink or executable-mode changes are never exempt. Ordinary README copy and listed engineering/screenshot instructions can change without replacing tested bytes. Acceptance JSON still passes every existing exact-candidate and human-observation check.

Promotion verifies the inventory against the candidate source, current main, and every intervening descendant tree. A protected change followed by a revert still requires a new candidate. Missing legacy inventories, changed dependencies, changed packaging, and mismatched provenance are refused. Main freshness and inputs are checked again after archive/mount verification, immediately before any tag/release mutation. Existing ancestry, signatures, asset hashes, human acceptance and unused-version gates remain. The Developer ID/notarization workflow is unchanged.
